# Portfolio QA Review

구현된 포트폴리오 랜딩페이지가 실제로 의도대로 동작하는지 검증하는 체크리스트.

## 원칙 — 존재 확인이 아니라 동작 확인

코드에 CSS 미디어쿼리가 있다고, GSAP 함수 호출이 있다고 통과시키지 않는다. 실제로 브라우저를 열고, 화면 폭을 바꾸고, 스크롤해서 **눈에 보이는 결과** 또는 **계측값**으로 확인한다. Playwright(`mcp__playwright__*` 도구)가 있으면 우선 사용한다.

## 체크리스트

### 1. 반응형

- [ ] 데스크톱(1440px 이상), 태블릿(~820px), 모바일(~390px) 세 폭에서 스크린샷을 찍어 비교한다.
- [ ] 텍스트가 잘리거나 겹치지 않는지(특히 긴 프로젝트명, 태그가 많은 카드).
- [ ] 터치 타겟(버튼/링크)이 모바일에서 충분히 큰지.
- [ ] 가로 스크롤이 의도치 않게 생기지 않는지(`body`에 `overflow-x` 발생 여부 확인).
- [ ] 내비게이션이 모바일에서 어떻게 동작하는지(햄버거 메뉴가 있다면 열림/닫힘까지 실제 클릭).

### 2. GSAP 애니메이션 동작

- [ ] 각 섹션을 실제로 스크롤해 등장 애니메이션이 발동하는지 확인한다(Playwright라면 `browser_evaluate`로 스크롤 후 요소의 `style`/`opacity` 값을 직접 읽어 확인 — 스크린샷 눈짐작보다 신뢰도 높음).
- [ ] 스크롤을 올렸다 내렸다 했을 때(`toggleActions`가 reverse라면) 자연스럽게 되감기는지.
- [ ] `prefers-reduced-motion: reduce` 설정 시 애니메이션이 실제로 생략/축소되는지(Playwright의 `emulateMedia` 또는 CDP로 시뮬레이션).

### 3. 성능 (버벅임)

- [ ] `PerformanceObserver`로 longtask(50ms 이상)를 계측하며 실제 스크롤(완만한 스크롤 + 빠른 연타 스크롤 양쪽)을 시뮬레이션한다.
- [ ] longtask가 발생하면 그 구간에서 애니메이션 중인 CSS 속성을 확인해 `gsap-scroll-motion` 스킬의 금지 패턴(filter/blur, 텍스트 scale 등)에 해당하는지 점검한다.
- [ ] 이미지가 있다면 실제 파일 크기가 과도하게 크지 않은지(수 MB급 원본 이미지를 그대로 쓰고 있지 않은지) 네트워크 탭으로 확인한다.

### 4. 접근성 기본기

- [ ] 시맨틱 태그(`header`/`nav`/`main`/`section`/`footer`) 사용 여부.
- [ ] 이미지에 `alt` 속성 존재 여부(장식용 이미지는 `alt=""`).
- [ ] Tab 키만으로 모든 인터랙티브 요소(링크/버튼)에 접근 가능한지, 포커스 시각 표시가 있는지.
- [ ] 색 대비가 텍스트/배경 간 충분한지(특히 어두운 배경 위 흐린 회색 텍스트 — 육안으로 의심되면 대비 확인).

### 5. Git/GitHub 연결

- [ ] `git status`로 미커밋 변경사항이 없는지(또는 있다면 의도된 것인지).
- [ ] `git remote -v`로 원격 저장소가 실제로 연결되어 있는지.
- [ ] `git log --oneline`으로 커밋 이력이 실제로 존재하는지.
- [ ] (원격 연결된 경우) GitHub 저장소 페이지에 실제로 코드가 반영되어 있는지 — 개발자의 "push했다"는 보고를 그대로 믿지 않고 `gh repo view` 또는 원격 확인.

## 재검증 규칙

버그를 발견해 개발자에게 보고한 뒤 수정 완료 알림을 받으면, **해당 항목만** 재검증한다(전체 체크리스트를 처음부터 반복하지 않음 — 단, 수정이 다른 섹션에 영향을 줄 수 있는 성격의 변경이면 관련 항목도 함께 재확인).

같은 유형의 버그가 서로 다른 섹션에서 반복 발견되면(예: 반응형 깨짐이 프로젝트 섹션에 이어 스킬 섹션에서도 발생), patch 하나로 넘기지 말고 개발자에게 공통 원인(공용 컴포넌트/패턴의 구조적 문제)을 재검토하도록 명시적으로 요청한다.
