# Portfolio IA

포트폴리오 랜딩페이지를 처음 설계하거나 섹션을 추가/재구성할 때, 어떤 섹션을 어떤 순서로 배치하고 각 섹션에 무엇을 담을지 결정하는 방법을 안내한다.

## 왜 섹션 순서가 중요한가

방문자는 랜딩페이지를 스크롤하며 정보를 순서대로 습득한다. 첫 화면(히어로)에서 "누구인지 + 무엇을 하는지"를 즉시 전달하지 못하면 이탈한다. 반대로 프로젝트를 먼저 보여주고 소개를 나중에 하면, 방문자가 맥락 없이 결과물만 보게 되어 설득력이 떨어진다. 표준 순서(아래)는 임의 관습이 아니라 "신뢰 형성 → 증거 제시 → 행동 유도"의 자연스러운 흐름을 따른다.

## 표준 섹션 구조

포트폴리오 성격(개발자/디자이너/기획자 등)에 따라 가감하되, 기본 골격은 다음과 같다:

1. **히어로(Hero)** — 이름/직군 한 줄 + 핵심 가치 제안 한 문장 + CTA(스크롤 유도 또는 연락하기). 첫 화면에서 스크롤 없이 보여야 한다.
2. **소개(About)** — 짧은 자기소개, 강점 3~4가지, 사용 스택/툴.
3. **프로젝트(Projects)** — 반복 가능한 카드 구조: 프로젝트명, 한 줄 요약, 사용 기술 태그, 대표 이미지/스크린샷, 링크(라이브/GitHub). 3~6개 정도 들어갈 수 있게 설계한다.
4. **스킬/경력(Skills/Experience)** — 기술 스택을 카테고리별로 묶거나, 타임라인 형태의 경력 요약.
5. **연락처(Contact)** — 이메일/소셜 링크 + CTA 버튼. 폼이 필요하면(백엔드 없는 정적 사이트이므로) `mailto:` 링크나 외부 폼 서비스 연동 여부를 명시한다.

내비게이션은 이 섹션들을 앵커 링크(`#projects` 등)로 연결한 단일 페이지 스크롤 구조가 기본값이다.

## 콘텐츠 필드 명세 작성법

각 섹션마다 "필드"를 표로 정의한다 — 나중에 실제 콘텐츠를 채울 사람이 무엇을, 몇 개까지 넣어야 하는지 헷갈리지 않게 하기 위함이다.

| 필드명 | 설명 | 반복 가능 | 플레이스홀더 예시 |
|--------|------|-----------|---------------------|
| 프로젝트명 | 카드 제목 | 3~6개 반복 | "프로젝트 A" |
| 한 줄 요약 | 카드 부제 | 프로젝트당 1개 | "[이 프로젝트가 해결한 문제를 한 문장으로]" |
| 기술 태그 | 카드 하단 배지 | 프로젝트당 3~6개 | "React", "GSAP" |

## 플레이스홀더 작성 원칙

실제 콘텐츠가 없는 초기 단계에서는:
- **자리표시자임이 명확해야 한다** — "홍길동", "삼성전자 인턴 6개월" 처럼 실존할 법한 가짜 정보를 지어내지 않는다. "[이름을 입력하세요]", "회사명 A" 같이 채워 넣을 자리임이 드러나는 표기를 쓴다.
- **구조는 실제처럼 견고하게** — 필드 개수/길이 제한은 실제 콘텐츠 기준(예: 요약은 1~2문장, 40자 내외)으로 잡아, 나중에 진짜 내용을 넣었을 때 레이아웃이 깨지지 않게 한다.
- **이미지 자리는 비율을 명시** — "프로젝트 썸네일 (16:9)"처럼 실제 이미지가 들어갈 비율/크기를 명세해 디자이너·개발자가 레이아웃을 그 기준으로 짜게 한다.

## 스크롤 애니메이션을 고려한 설계

GSAP ScrollTrigger로 섹션별 등장 연출이 들어갈 것을 전제로, 한 섹션에 정보를 과밀하게 몰아넣지 않는다 — 각 섹션이 뷰포트 높이 기준으로 한 번에 인지 가능한 정보량을 담아야 애니메이션 타이밍이 자연스럽다.
